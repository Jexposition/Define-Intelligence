# How to read the repository map

## Start here

Open [`REPOSITORY_ARCHITECTURE_MAP.html`](REPOSITORY_ARCHITECTURE_MAP.html) in a browser. It is the interactive reading view for the complete Lean tree.

The page has five useful controls:

- search by module name, source path, declared object, or inferred role;
- filter by source family (`NavierStokes`, `Euler`, review code, and so on);
- show only modules joined to the selected endpoint;
- search all 50,191 declarations and open the exact source line;
- ask for a directed import path between two modules;
- expand a module card to see its imports, reverse dependents, declarations, source flags, and source link.

For a printable explanation, read [`REPOSITORY_ARCHITECTURE_MAP.md`](REPOSITORY_ARCHITECTURE_MAP.md). For the exhaustive text archive, use [`LEAN_MODULE_EXPLANATIONS.md`](LEAN_MODULE_EXPLANATIONS.md). Every Lean file has one card in that archive.

## What the map means

### Scoped endpoint reachability

In the semantic coverage register, `reachable` is a scoped graph label. It means that a module was reached by the captured import/declaration closure rooted at the selected endpoint audit roots, currently the `NavierStokesR3.theorem_1_1` path and its captured `ActualCandidateAssembly.selected_witness` path. `unreachable` means only that the module was not reached by those roots. It does **not** mean that the source file is absent, invalid, dead, unbuildable, or unreachable from every other OpenAI entry point.

All indexed source modules remain in scope. Modules outside the selected endpoint closure receive a separate source-and-scope audit covering their imports, declarations, paper relevance, alternative entry points, admitted material, and relation to the exported endpoint.

The map separates three kinds of information:

1. **Exact source facts:** file path, line count, declarations, imports, reverse dependents, source flags, and source-to-environment joins.
2. **Compiled-route facts:** whether the module was joined to the captured environment for `NavierStokesR3.theorem_1_1`.
3. **Navigation summaries:** short role descriptions inferred from file names and declaration names. These help a reader find the relevant mathematics; they are not proof interpretations.

The central review distinction is:

\[
\text{dependency reachability}
\neq
\text{value-level transport of an invariant}.
\]

For example, a moment-repair file can be reachable from `selected_witness` without the exported witness proving that the same moment, evaluated on the final Cartesian field after localisation and summation, has the required value. The map therefore identifies both the route and the question that remains to be checked.

## Recommended mathematical reading order

1. Read `NavierStokes/R3/ProblemStatement.lean` to identify the formal candidate predicate.
2. Read `NavierStokes/R3/Theorem.lean` to see how the endpoint packages that predicate.
3. Follow `NavierStokes/ActualCandidateAssembly.lean` and `selected_witness` into the concrete construction.
4. Follow the germ, stage, potential, wave, and temporal families to understand how fields are assembled.
5. Follow `FiveRowRank.lean`, `PositiveOrderMoments.lean`, `FiveProfileMoments.lean`, `MeanRankUpdate.lean`, and `DefectIncrementBounds.lean` for the correction and moment branch.
6. Follow `MixedPeriodicAssembly.lean` and the localisation/cutoff families into velocity, pressure, and residual assembly.
7. Follow the `R3*` files for whole-space packaging, pressure, energy, decay, and comparison consequences.
8. Compare every advertised paper invariant with an explicit theorem on the final exported fields, not merely with a reachable upstream declaration.
9. Use the declaration finder for theorem/definition names, then use the route excerpt and source link to inspect hypotheses and proof terms.

## Evidence authority order

When the readable summary and a source claim disagree, use this order:

1. the hashed tree inventory from `tree-maker/Define inteligence tree.md`;
2. the live source file and its SHA-256 identity;
3. the source declaration/import map;
4. the elaborated Lean environment exported from `NavierStokesR3.theorem_1_1`;
5. the exact-name source/environment join;
6. the claim register and review prose.

The readable map is therefore a guide into the evidence, not a replacement for it.

## Reproduce the reading layer

From the repository root, run:

```powershell
NavierStokesReview/src/audit/run_hardened_audit.ps1
```

The run regenerates the raw machine map first and then regenerates the Markdown,
HTML, declaration index, DOT, and LaTeX reading layers from that same map. If a source file changes,
the map should be regenerated before any review conclusion is updated.

## Review boundary

The map can establish that a file exists, that declarations and imports connect,
and that a declaration is or is not present in the selected compiled closure. It
cannot by itself establish a mathematical identity, a physical interpretation,
or a contradiction. Those require a theorem-level source audit and, where
needed, a zero-sorry Lean result.

## Dual graph and mathematical reading layer

Open [`MATHEMATICAL_SPECIFICATION.md`](MATHEMATICAL_SPECIFICATION.md) for the notation and endpoint route before reading the raw graph. The browser map is the human interface; `NavierStokesReview/evidence/repository_audit_graph_2026-09-26.json` is its declaration-level evidence record.

The graph has two populations: declarations parsed from current Lean source and declarations captured from the elaborated environment. It joins them only by fully qualified name and source identity. Compiled-only declarations, ambiguous matches, omitted type text, and missing docstrings remain explicit metadata states rather than being guessed away. The ordinary graph is a compact query view. Every captured elaborated type is retained in the compressed companion `NavierStokesReview/evidence/repository_audit_graph_2026-09-26_full.json.gz`; the exact endpoint import result is recorded separately in `NavierStokesReview/evidence/direct_endpoint_closure_validation_2026-09-29.md`.

| Edge | Meaning | Does not prove |
|---|---|---|
| `MODULE_IMPORT` | One Lean module imports another. | An invariant is transported through the import. |
| `COMPILED_DECLARATION_USE` | The captured environment records one declaration using another. | The used declaration has the paper's intended physical interpretation. |

The map therefore lets a mathematician follow `selected_witness`, `CandidateProperties`, `FiveRows`, `scaleDebt`, `barMoment`, residuals, pressure, energy, and the `R3` packaging without turning reachability into a semantic theorem.
